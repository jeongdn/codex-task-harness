# 설계 먼저, 승인 후 구현

사용자가 이 단계의 설계를 이해하고 결정하는 것이 목표다. 사용자가 고른 것이 정답이고, AI는 근거 있는 선택지를 낸다.

## A. 설계 제안 (코드 쓰지 않음)

1. AGREEMENT.md, PLAN.md, DESIGN.md를 읽고 이번 단계 하나만 고른다. 사용자가 단계를 말했으면 그 단계.
2. 아래 형식으로 채팅에 보여 준다. 40줄 이내, 전문 용어는 처음 나올 때 한 줄로 풀어 쓴다.

```
[n단계 설계] (이 단계가 해결하는 담당자 요구: R·M 번호)

만들 것
| 함수(또는 화면·API) | 입력 → 출력 | 하는 일 한 줄 |

방법
- 쓸 알고리즘·규칙: (예: 시간대별로 묶은 뒤 가까운 정류장부터 붙이는 탐욕 배정)
- 고른 이유: (담당자 말 또는 데이터 근거)
- 다른 선택지와 버린 이유: (예: 최적화 라이브러리는 설치 제약 때문에)

정할 것 (사용자가 고르기)
- A안 … / B안 … → 결과가 어떻게 달라지는지 한 줄. 내 추천과 이유.

데이터 흐름
입력 파일 → 함수A → 함수B → 화면/출력

테스트로 확인할 것
- (성공 기준이나 경계값 2~3개, 기대 결과 숫자까지)

바꿀 파일 / 설치할 것(없으면 '없음') / 예상 시간
```

3. 사용자에게 묻는다: "어느 안으로 갈까요? 바꾸고 싶은 함수·방법이 있으면 말해 주세요." 그리고 멈춘다.
4. 승인은 "진행", "승인", "B안으로 해"처럼 분명한 말일 때만이다. 질문이면 답하고, 수정 요청이면 설계를 고쳐 다시 보여 준다. 승인 전에는 파일을 만들거나 고치지 않는다.

## B. 승인 후 구현

5. 승인된 설계를 DESIGN.md의 해당 단계 칸에 옮긴다. 사용자가 고르거나 바꾼 점은 "사용자 결정:"으로 적고, 이유는 사용자가 한 말 그대로 DECISIONS.md에도 한 줄 남긴다. 사용자가 이유를 말하지 않았으면 한 줄로 묻는다.
6. 설계에 적힌 것만 구현한다. 하다가 설계와 달라져야 하면 멈추고 무엇이 왜 다른지 말한 뒤 다시 승인을 받는다.
7. 테스트를 먼저 쓰고, 구현하고, `python3 -m unittest discover -s tests -v`로 실행한다. 명령과 결과를 보여 준다.
8. PLAN.md의 이 단계 상태를 '완료'로 바꾸고, 바꾼 파일만 `git add <파일>`로 올려 커밋한다: `git commit -m "[n단계] 무엇을 / 왜 (테스트 n/n 통과)"`

## C. 이해 확인 (구현 직후)

9. 채팅에 보여 준다.
   - 내 말로 3줄: 이 단계는 무엇을 하고, 핵심 함수는 어떻게 동작하고, 무엇으로 확인했나.
   - 직접 보는 법: 실행 명령 한 줄, 또는 화면에서 눌러 볼 곳.
   - 확인 질문 1개: "만약 ~이면 이 코드는 어떻게 될까요?" 처럼 사용자가 답해 볼 질문. 답은 먼저 말하지 않고, 사용자가 답하면 맞는지 코드 근거와 함께 알려 준다.
10. 다음 단계로 가기 전에 사용자가 "다음"이라고 할 때까지 기다린다.
